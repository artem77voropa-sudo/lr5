## Вступ

Мета роботи — дослідити шлях недовірених даних від введення та збереження до відображення у браузері й усунути небезпечне тлумачення тексту як HTML. На власному трекері інцидентів перевіряються опис інциденту та текст коментаря, налаштовується доступ між різними browser origins і застосовуються захисні HTTP-заголовки.

## DEL-01: реалізація й докази

Карта двох потоків: [source-to-sink.md](source-to-sink.md). Детальні результати, REG-XSS-01, REG-CORS-01, CORS/CSP та межі висновків: [browser-security-evidence.md](browser-security-evidence.md).

Початкові innerHTML для Description і Comment.Text дозволяли нешкідливому локальному marker створити img та змінити атрибут прихованого елемента. Обидва sinks замінено єдиним renderPlainText через textContent. Marker після виправлення показується як текст; позитивні перевірки апострофів, лапок, HTML-подібного тексту, Unicode і граничного опису пройшли.

Development policy дозволяє точний origin localhost:4173, GET, X-Lab-Cors-Probe й credentials. Для localhost:4174 браузер не надає response JavaScript. Перевірено preflight, cookie-запит після входу, анонімну відмову 401 та тимчасову відсутність AllowCredentials. Остаточна policy відновлена. CSP працює в enforcement; додатково перевірено nosniff, no-referrer і frame-ancestors 'none'. Інтеграційна регресія: 90 успішних тестів, 0 помилок.

## DEL-03: контрольні відповіді

1. **Чому дані з БД недовірені?** Вони могли надійти від користувача. Збереження не змінює їхній зміст і не робить їх безпечним HTML.
2. **Source, transformation, sink?** Для опису source — поле форми, transformation — binding/валідація/Trim і JSON, storage — incidents.description, sink — DOM опису. Для коментаря source в цьому досліді — навчальний seed, storage — incident_comments.text, sink — створений p.
3. **Види XSS?** Stored зберігає введення для наступного читання; reflected повертає його в поточній відповіді; DOM-based описує небезпечне перетворення у клієнтському DOM. Тут збережений текст потрапляв у клієнтський innerHTML, тому характеристики можуть поєднуватися.
4. **Чому блокування script недостатнє?** Інші HTML-конструкції, наприклад обробники подій, також можуть виконувати код. Треба усунути небезпечний sink.
5. **textContent чи sanitizer?** Для звичайного тексту — textContent. Якщо контракт свідомо дозволяє форматований HTML, потрібен підтримуваний sanitizer із чіткою policy; у цій роботі HTML не дозволяється.
6. **Чому не regex sanitizer?** HTML має складні правила розбору й контексти; регулярний вираз не є повноцінним HTML parser та легко пропускає варіанти розмітки.
7. **Origin?** Схема, host і port. localhost:4173 та localhost:5080 — різні origins.
8. **Preflight?** Браузер сам надсилає OPTIONS з Origin, Access-Control-Request-Method та, за потреби, Access-Control-Request-Headers перед нестандартним cross-origin запитом.
9. **Хто реалізує CORS?** API оголошує дозволи заголовками; браузер перевіряє їх і вирішує, чи може JavaScript прочитати response та чи можна надсилати actual запит після preflight.
10. **Чому curl читає?** Це прямий HTTP-клієнт, він не застосовує браузерну same-origin/CORS-межу.
11. **Чому CORS не authorization/CSRF?** CORS не визначає користувача та власника ресурсу, а деякі небажані запити можуть бути надіслані навіть без права прочитати відповідь. Потрібні окремі серверні перевірки доступу й CSRF-контроль.
12. **Wildcard і credentials?** Для credentialed response браузер потребує конкретного дозволеного origin та Allow-Credentials:true, а не '*'. Дозволено лише погоджений localhost:4173.
13. **Межа CSP?** CSP обмежує джерела та виконання ресурсів як додатковий бар'єр. Помилковий DOM sink усе одно треба виправляти; це підтверджено окремим тестовим браузером без CSP.
14. **Заголовки?** nosniff стримує підміну тлумачення MIME; no-referrer не передає Referer; frame-ancestors 'none' забороняє embedding. Вони не замінюють safe rendering чи серверну авторизацію.

## Висновок

У роботі простежено два шляхи недовіреного тексту від джерела через PostgreSQL та JSON до DOM. На локальному marker відтворено небезпечну поведінку innerHTML, після чого опис і коментарі переведено на спільний helper із textContent. Той самий рядок більше не створює HTML-елементів, а звичайний текст зберігає правильне відображення.

Для браузерного доступу налаштовано точну Development CORS policy та перевірено різницю між дозволеним і недозволеним origin, простим запитом, preflight і cookie credentials. Досліди показали, що браузерне блокування читання відповіді не рівнозначне відсутності HTTP-запиту й не замінює authentication, authorization або CSRF-захист.

Додатково впроваджено enforcement CSP та перевірено захисні заголовки й основний клієнтський потік. Усі 90 інтеграційних тестів пройшли, результати браузерних перевірок збережено окремо. Висновки стосуються перевірених маршрутів і локального профілю; нові sinks і production-конфігурація потребують власної перевірки.
